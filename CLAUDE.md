## Architecture

A single-page, client-only trip-management app (React 19 + Vite 8 + TypeScript 6 + Tailwind v4). UI strings are Portuguese (pt-BR).

### No router — tab state drives everything

`App.tsx` renders every feature view conditionally off one `useState<NavTab>`. The `NavTab` union lives in `src/components/Navigation.tsx` and is the canonical list of screens. Adding a screen means: extend `NavTab`, add an entry to the `tabs` array in `Navigation.tsx`, and add a branch in `App.tsx`.

### TripContext is the entire data layer

`src/context/TripContext.tsx` (~850 lines) holds **all** application state and **all** CRUD operations for every entity. There is no store library, no data-fetching layer, and no per-feature state. Every view calls `useTrip()`.

Adding a new entity type touches five places in order:

1. `src/types/database.types.ts` — the interface
2. `src/services/initialMockData.ts` — the `INITIAL_*` seed export (some seeds instead live inline at the top of `TripContext.tsx`, e.g. `INITIAL_LUGGAGE`, `INITIAL_EXPENSES`, `INITIAL_DOCUMENTS`, `INITIAL_LOYALTY`)
3. `src/data/use<X>Data.ts` — the hook: fetches from Supabase scoped by `trip_id`/`tenant_id`, falls back to the `INITIAL_*` seed when the read comes back empty, and exposes add/update/delete that write through to Supabase (optimistic, with rollback + `recordFailure` retry on error) — plus a `src/data/mappers/<x>Mapper.ts` for DB-row ↔ TS-type conversion when the shapes differ
4. `TripContext.tsx` — call the hook and re-export what it returns
5. `TripContextType` — declare the new state and functions or they aren't reachable
6. The feature view + its modal

**Consequence:** seed data is only visible when the Supabase table is empty for that trip/tenant (no active tenant, or a fresh one) — editing `initialMockData.ts` has no effect once real rows exist. `currency`, `exchangeRate`, and `activeTripId` are the only remaining UI-only `localStorage` keys (see `STORAGE_KEY` in `TripContext.tsx`); no entity data lives there anymore.

### Supabase: everything is wired

The Supabase project is **`Nogaria_travel`** (ref `bkrqhividgljticgjrem`, region `us-west-2`, Postgres 17), in a *different* Supabase account/org than the one `.mcp.json` and the Supabase MCP server are authenticated as — the MCP tools cannot see this project. Use the **Supabase CLI** instead: it's linked (`supabase link --project-ref bkrqhividgljticgjrem`), and `.env` (git-ignored, not committed) holds `SUPABASE_URL` / `SUPABASE_PUBLISHABLE_KEY` / `SUPABASE_SECRET_KEY`. Useful commands: `supabase db query --linked "<sql>"`, `supabase db push --linked`, `supabase db advisors --linked --type security`.

The full schema is live remotely (5 migrations under `supabase/migrations/`), covering all ~19 entities from `database.types.ts`: `tenants`, `profiles`, `memberships`, `trips`, `participants`, `decisions`, `accommodations`, `flights`, `transport_reservations`, `itinerary_items`, `gift_cards`, `purchase_items`, `luggages`, `expenses`, `tasks`, `documents`, `loyalty_accounts`, `ai_provider_configs`, `ai_usage_logs`, plus `audit_finding_resolutions` (a DB-backed home for the `resolved` toggle audit findings already have client-side — findings themselves stay computed, not stored) and `tenant_invites` (pending team invites, see below). RLS is enabled on every table; access is entirely via `memberships` → `tenants` → `trips` (helper functions `is_tenant_member`/`is_tenant_admin`/`is_trip_member`). These are **`SECURITY DEFINER`**, not `INVOKER` — they were originally invoker-rights, but `memberships_select`'s policy calls `is_tenant_member`, whose body queries `public.memberships`; as an invoker-rights function that inner query was itself subject to `memberships_select`, recursing until Postgres raised `54001: stack depth limit exceeded` (surfaced by PostgREST as a 500) on every login. Fixed in `20260726150000_fix_rls_helper_recursion.sql` by making them `SECURITY DEFINER` (owned by `postgres`, which bypasses RLS since `memberships` has no `FORCE ROW LEVEL SECURITY`) — any future RLS helper function that queries the same table its policy protects needs this same treatment, or it will recurse the same way. Only `authenticated` and `service_role` are granted anything — **no `anon` access anywhere**, since this project post-dates Supabase's 2026-04 change that stopped auto-granting new public tables to any role, and this app has no public/anonymous use case. New tenants must go through the `create_tenant_with_owner(p_name text)` RPC (`SECURITY DEFINER`, `authenticated`-only, slug derived internally from the name) rather than inserting into `tenants` directly, since a bare INSERT policy on `tenants` would let any authenticated user join without a matching membership.

Deliberate deviations from the TS types, worth knowing before writing queries or wiring the client:
- `participants.age` is **not a column** — only `birth_date` (avoids the drift bug noted below under Gotchas). Compute age at the application layer.
- `gift_cards.cashback_amount` / `net_cost` / `effective_savings` / `effective_savings_pct` are Postgres **generated columns**, computed identically to `giftCardCalculator.ts` — don't set them on insert/update, Postgres rejects writes to generated columns.
- `ai_provider_configs` / `ai_usage_logs` carry a `tenant_id` column not present on the TS interfaces — required for RLS row isolation, since without it these tables would have no way to scope access per tenant.

**What's actually wired:** `src/services/supabaseClient.ts` creates the client from `VITE_SUPABASE_URL` / `VITE_SUPABASE_PUBLISHABLE_KEY` — Vite only exposes env vars to client code when they're `VITE_`-prefixed, so these are distinct from the unprefixed `SUPABASE_*` vars the CLI uses. `src/context/AuthContext.tsx` owns the session (via `supabase.auth.onAuthStateChange`, the single source of truth for session state — there's no separate `getSession()` call, since `onAuthStateChange` already delivers the initial session as an `INITIAL_SESSION` event to new subscribers), the signed-in user's `profile`, and their `tenantMemberships`/`activeTenantId`/`activeRole`. `src/features/auth/AuthGate.tsx` gates the whole app on that state: unauthenticated → `AuthScreen` (email/password, magic link, Google OAuth — Google needs the provider enabled and redirect URLs configured in the Supabase dashboard, not just client code), authenticated with zero tenants → `OnboardingScreen` (calls `createTenant`, which wraps `create_tenant_with_owner`), a failed profile/membership fetch → a retry screen, otherwise the app itself. `src/components/modals/TeamModal.tsx` reads/writes `memberships` and `tenant_invites` directly for the active tenant (list members, invite by email, cancel a pending invite) and is gated to admins for the invite/cancel actions via `activeRole`.

**All collections are wired to Supabase** via one hook per entity in `src/data/use<X>Data.ts` (+ a mapper in `src/data/mappers/`), each with optimistic writes and a `recordFailure` retry path surfaced by `WriteFailureBanner`. IDs come from `crypto.randomUUID()` (`src/services/ids.ts`). Since #34 **no hook falls back to `initialMockData.ts`** when a collection comes back empty — a new tenant sees `EmptyState` boxes, not the author's Orlando trip; the seed file is kept only as fixture material. `TripContext.tsx` still mirrors each collection into `localStorage` (write-only relics, nothing reads them back; PR #48 removes them). Logging out clears the Supabase session and every `localStorage` key under the `STORAGE_KEY` prefix.

### Services (`src/services/`) — pure functions, two different timings

- **`auditEngine.ts`** — `runFullTripAudit()` derives `AuditFinding[]` from the whole trip. Called inside a `useMemo` in `TripContext`, so findings recompute on every data change; `rerunAudit()` is intentionally a no-op. Only the *resolved* flags are persisted (as an ID array in `resolvedAuditIds`), never the findings themselves. The unresolved count feeds the Audit tab badge in `App.tsx`.
- **`coverageEngine.ts`** — same pattern as `auditEngine.ts`: `computeCoverage(items, participants)` derives per-type and per-participant done/total counts (plus an overall percent) from `ItineraryItem.participant_status`, called on every render from `src/features/timeline/` (the "Cronologia" tab's `DayTimeline`/`MonthCalendar`), never persisted. Eligibility (`min_height_cm`/`min_age_years` vs. the participant) gates the per-participant denominator, generalizing the height-alert comparison `ItineraryView.tsx` already does for Gabi — but as of the roteiro-dos-parques data, no park item actually sets `min_height_cm`/`min_age_years`, so that eligibility gate is unexercised by real data today.
- **`giftCardCalculator.ts`** — applied at **write** time, not render time. `addGiftCard`/`updateGiftCard` in the context recompute and store `net_cost`, `cashback_amount`, `effective_savings`, `effective_savings_pct` on the record. Any new code path that mutates a gift card must recompute these or the denormalized fields go stale.
- **`exchangeRateService.ts`** — `fetchLiveExchangeRate(fallback, client)` resolves USD/BRL in a cascade: 30-min `localStorage` cache → latest **PTAX** row in `public.exchange_rates` (written by the `exchange-rate-sync` edge function from the BCB Olinda API, scheduled by pg_cron on weekdays; rows older than 7 days are ignored) → live market rate (AwesomeAPI) → the fallback. The origin is exposed as `exchangeRateSource` on `useTrip()` and shown in the DRE header next to the "custo real no cartão" (`cardEffectiveRate`, IOF 3.5%). `DEFAULT_EXCHANGE_RATE = 5.62` is the last resort only. **Expenses freeze the day's rate at creation** (`ExpenseModal` receives `defaultExchangeRate`); editing keeps the stored rate — old expenses never recompute retroactively (#32).

### Currency convention

**All monetary values are stored in USD.** Conversion and formatting happen at render time via `formatAmount(usd)` / `convertAmount(usd)` from `useTrip()`, driven by the user's `currency` toggle and `exchangeRate`. Never store BRL into a USD field. (`Expense` is the exception — it carries `amount`, `amount_usd`, `amount_brl`, and `exchange_rate` together.)

### View / modal pattern

Each `src/features/<domain>/<Name>View.tsx` owns its modal open/close state and a `editingX: X | null`. The same modal serves create and edit: `null` initial data means create. Views filter their collection by `activeTrip.id` themselves — the context stores entities for *all* trips unfiltered.

All modals wrap `components/modals/BaseModal.tsx`, which supplies the overlay, header, Escape-to-close, and body-scroll lock. Modals live in the shared `components/modals/` directory, not next to their feature.

`src/features/itinerary/ItineraryView.tsx` (the "Roteiro Diário & Atrações" screen) is a variant of this pattern: it owns `viewMode` (`'list' | 'timeline' | 'calendar'`) and `timelineDate`, and composes two presentational sub-components (`DayTimeline.tsx`, `MonthCalendar.tsx`) that take props rather than calling `useTrip()` for their data (though `DayTimeline` does call `useTrip()` for `updateItineraryItem`, since it owns the participant-status click handler). Cronologia and Calendário consider **all** itinerary items, not just parks — the park-only filter was removed in `8a85586`, and the Cronologia tab has day-selector chips for every date present in the itinerary.

### Styling

Tailwind v4 via the `@tailwindcss/vite` plugin; `src/index.css` uses `@import "tailwindcss"` and defines the `.glass-panel` / `.glass-card` utilities the UI leans on heavily.

`tailwind.config.js` is **effectively dead**: under Tailwind v4 it isn't auto-loaded, there is no `@config` directive, and nothing in `src/` uses the semantic tokens it defines (`bg-primary`, `text-foreground`, …). The HSL variables in `index.css` `:root` are likewise unused. Match the existing code: raw palette classes (`slate-*`, `blue-*`, `rose-*`, `amber-*`, `emerald-*`) on a dark background, plus the glass utilities. `src/App.css` is orphaned — nothing imports it.

Icons are `lucide-react` throughout (16 files). `recharts`, `date-fns`, `clsx`, and `tailwind-merge` are installed but **unused** — prefer them over new dependencies if you need charts, date math, or class merging.

## WhatsApp Bot (NLP via Gemini + Meta Cloud API)

Added 2026-08-25. The bot answers trip questions, sends the daily activity list, and delivers reminders via WhatsApp. AI is **Gemini** (`gemini-3.5-flash`, same REST v1beta pattern as `price-research`, costs logged to `ai_usage_logs` with `function_name: 'whatsapp_bot'`).

**Constraint that shaped the design:** the official Meta Cloud API does **not** support groups — delivery is 1:1 to each participant's `participants.whatsapp_phone`. (A group-capable Evolution API variant was considered and rejected.)

Layout:
- `supabase/functions/whatsapp-webhook/index.ts` — public (`verify_jwt = false` in `config.toml`). GET handles Meta's `hub.verify_token` challenge; POST verifies `X-Hub-Signature-256` (HMAC-SHA256 with `META_WA_APP_SECRET`, skipped when the secret is unset; a failed check is logged with `console.warn`, since a rotated App Secret otherwise looks like total silence), extracts text messages, **returns 200 immediately** and processes each message inside `EdgeRuntime.waitUntil()` (Meta re-sends and eventually unsubscribes webhooks that answer slowly; Gemini + tools + send takes tens of seconds, so results only appear in the function logs, never in the HTTP response), dedupes on `whatsapp_messages.wa_message_id` (unique — Meta retries webhooks), resolves tenant via `whatsapp_configs.phone_number_id`, then calls Gemini with **function calling** and replies. The model comes from the tenant's active `ai_provider_configs` row filtered to `provider = 'gemini'` and passed through `resolveGeminiModel()` (`_shared/gemini.ts`), which falls back to the default for empty, non-`gemini-*`, or `1.5`/`2.5` names — `model_name` is free text in the Copiloto UI and now syncs to Supabase, so an OpenAI/Claude config or a typo there used to send a nonexistent model name to the Gemini API (HTTP 404). Conversation history excludes the message being answered (it's inserted first, for idempotency) and is run through `sanitizeHistory()`; the model turn echoed back with tool results goes through `buildModelTurnParts()`, which keeps `thoughtSignature` (mandatory on Gemini 3.x function calls) and drops empty parts (`{ text: '' }` is rejected with HTTP 400).
- `supabase/functions/daily-digest/index.ts` — public, gated by `x-cron-secret` header. Sends the day's itinerary + reminders (tasks due ≤ 48h, flights ≤ 24h, height alerts for the youngest minor) to every participant with a phone, at each tenant's `digest_time`/`timezone`. Scheduled by pg_cron (`'whatsapp-daily-digest'`, hourly) in `20260825130000_daily_digest_cron.sql`, which reads `project_url`/`cron_secret` from **Vault** and skips with a WARNING if absent.
- `supabase/functions/_shared/` — `formatter.ts` (digest text, pure), `tripContext.ts` (context loader + system prompt; `localDateIso` is timezone-aware), `gemini.ts` (tool-calling loop, max 4 rounds), `tripTools.ts` (5 tools: `get_itinerary`/`get_tasks`/`get_flight_info` read; `mark_itinerary_item_done`/`complete_task` write — all args strictly validated before touching the DB), `whatsappClient.ts` (Meta send adapter).
- Tables: `whatsapp_configs` and `whatsapp_messages` (both tenant-scoped RLS, same pattern as `ai_provider_configs`); `participants.whatsapp_phone` added in `20260825120000_whatsapp_integration.sql` and mapped in `participantMapper.ts`.

### Avisos de atividade e caminho quente do bot (2026-09-06)

Duas frentes aplicadas sobre o bot acima: latência/acurácia do caminho quente, e avisos de atividade **por horário** (o digest já cobria o *por dia*).

**Latência.** `buildSystemPrompt` agora injeta o roteiro do dia, as tarefas ≤48h e o voo ≤24h direto no prompt — dados que `fetchTripContext` já carregava e descartava. A pergunta mais frequente ("o que a gente faz hoje?") passa de 2 chamadas ao Gemini para 1, porque o modelo não precisa mais chamar `get_itinerary` para hoje. O prompt foi reordenado em `STATIC_PROMPT` (prefixo fixo) + bloco `--- CONTEXTO DE HOJE ---`: prefixo estável é o que o cache implícito do Gemini reaproveita. Há teste garantindo que o prefixo é byte-idêntico entre chamadas.

**Confiabilidade.** `generateContent` ganhou `AbortSignal.timeout(25s)` e 3 tentativas com backoff (400/800ms) em 429/5xx/rede — 4xx de configuração não repete. E `processMessages` agora manda uma mensagem de fallback ao usuário quando o processamento falha: como o 200 já foi devolvido à Meta, ela não reenvia, então antes disso uma falha do Gemini era **silêncio absoluto** do lado da família. A telemetria pós-envio (`whatsapp_messages` + `ai_usage_logs`) foi isolada num try/catch para não escalar e disparar o fallback por cima de uma resposta que deu certo.

**Acurácia (entity resolution).** O `ilike '%título%'` das tools de escrita foi trocado pelas RPCs `search_itinerary_items(p_trip_id, p_query, p_date, p_limit)` e `search_tasks(p_trip_id, p_query, p_statuses, p_limit)` — `unaccent` + `pg_trgm`, ranqueando por `greatest(word_similarity, similarity, bônus de substring)`. `word_similarity(query, título)` é a métrica certa porque mede o casamento da query com um *trecho* do título ("everest" → "Expedition Everest" = 1.00). Validado contra Postgres real: `ilike` devolvia **zero** para "montanha russa" (hífen), "expediton everest" (typo) e "almoco" (sem cedilha); as RPCs devolvem 1.00 / 0.75 / 1.00. O piso de score é **0.45**, calibrado empiricamente — em 0.3, "check-in" casava "Comprar chip internacional" com 0.33.
`resolveMatch()` (`tripTools.ts`) decide entre agir e perguntar: escreve só se o melhor candidato tem score ≥ 0.6 **e** está ≥ 0.15 à frente do segundo. Empate técnico ou candidato único fraco viram desambiguação — falso positivo numa tool de escrita é pior que uma pergunta a mais. Ler `search_*` no app é seguro por RLS (são `SECURITY INVOKER`, ao contrário dos helpers `is_*_member`).

**Avisos por horário.** `supabase/functions/activity-reminders/index.ts` (público, `verify_jwt = false`, gated por `x-cron-secret`), agendado por pg_cron nos minutos `2,9,16,23,30,37,44,51,58` (passo de ~7 min) para não concorrer com o digest (minuto 7). Toda a lógica de janela vive em `_shared/reminderScheduler.ts`, que é **puro e testado** (28 testes) — a function só faz I/O.
- **Janela aberta, não fatiada:** envia quando `0 < minutosAté <= lead`, não quando o item cai numa fatia do cron. Execução perdida é recuperada pela seguinte; atividade já iniciada nunca gera aviso atrasado.
- **Idempotência é do banco:** a chave única de `activity_reminders` `(itinerary_item_id, participant_id, kind)` é o que garante envio único. A function *reserva* a linha antes de enviar e a **apaga se o envio falhar**, para a próxima execução tentar de novo (ordem inversa mandaria o aviso duas vezes, que é o erro mais visível para a família).
- **Antecedência em cascata:** `itinerary_items.reminder_minutes_before` (override, `0` desliga) → senão `max(whatsapp_configs.reminder_lead_minutes, recommended_arrival_min_before + 15)`. **Bug real de produção corrigido em `20260907000000_fix_reminder_cadence_alignment.sql`:** o cron original batia em passo de 10 min (`3,13,23,...,53`) — mesmo fator dos horários redondos de um roteiro típico (17:20, 18:00, 19:30, ...) e da antecedência padrão (60min, múltiplo de 10). O primeiro tick depois de `horário - lead` caía *sempre* 3 min depois do limiar, e todo aviso saía com "Daqui a 57 min!" — não uma variação entre 50-60 como o design original assumia, mas um valor travado, o que a família (corretamente) leu como bug. Passo de 7 min (coprimo de 10) faz esse deslocamento rotacionar por 7 valores diferentes conforme o horário da atividade, em vez de travar sempre no mesmo — testado em `activityReminders.test.ts` (`cadência do cron vs. horários redondos`).
- **Silêncio adia, não cancela:** `quiet_hours_start`/`quiet_hours_end` (default 22:00–07:00, com virada de meia-noite). Um aviso represado sai na primeira rodada após a janela, se a atividade ainda não começou.
- Tool `set_activity_reminder` permite ajustar isso pelo WhatsApp ("me avisa 30 min antes do jantar").
- `reminder_minutes_before` atravessa o app desde `20260909` (`ItineraryItem` → `itineraryMapper` → campo "Aviso no WhatsApp (min)" no `ItineraryModal`). O campo vazio na UI grava `null` (cascata padrão do bot) e `0` grava zero (aviso desligado) — a distinção importa, porque tratar `0` como ausente faria todo item silenciado voltar a falar.

### Dias operacionais e o diretório `supabase/seeds/` (2026-09-09)

`buildParkDay` (em `roteiro/shared.ts`) distribui as atrações uniformemente entre abertura e fechamento — serve para catalogar um parque, não para operar um dia real, onde os horários são decididos por fila de rope drop, âncora de reserva e tempo de travessia a pé. `buildOperationalDay`, no mesmo arquivo, recebe horários explícitos por bloco (`OperationalRow`) e força `lightning_lane: 'none'` em todos eles: um dia operacional só existe porque não há fila paga para reordenar o roteiro. Blocos sem `item_type` (deslocamento, pausa) saem com `counts_toward_completion: false`, para não diluir a métrica de cobertura.

O primeiro é `roteiro/epcotDia09.ts` (EPCOT, 09/09/2026, sem Early Entry e sem Lightning Lane). **A regra que mais afeta a família:** o bot dispara um WhatsApp por item para *cada* participante, então um dia de 32 blocos com `reminder_minutes_before` indefinido viraria 32 mensagens por pessoa. Por isso o default no módulo é `0` (desligado) e só 9 momentos de decisão avisam — a saída do hotel, o rope drop, a travessia para o World Showcase, a reserva, e as atrações que não têm segunda janela no dia. Há teste travando essa lista e garantindo que nenhum item fique com o valor indefinido.

Como `itinerary_items` vive no Supabase e não há semeadura automática, o dia também existe como SQL em `supabase/seeds/roteiro_epcot_2026-09-09.sql`, **gerado a partir do módulo TS** (editar o TS e regerar, não editar o SQL à mão). O script resolve viagem e participantes por consulta em vez de hardcodar UUIDs, e é idempotente: apaga os itens do EPCOT já existentes naquela data antes de inserir — o que também descarta os `participant_status` do dia, então rodar antes de o dia começar.

**Colunas e índices novos** (`20260906120000_bot_performance_and_reminders.sql`): índice composto `whatsapp_messages (tenant_id, sender_phone, created_at desc)` — o `loadHistory` filtrava por três coisas com índices de coluna única; `whatsapp_messages.kind` (`chat`/`digest`/`reminder`), com `loadHistory` filtrando `kind = 'chat'` para que digests e avisos não entrem no histórico do modelo como turnos de conversa; `itinerary_items (trip_id, date, time_start)`; `ai_usage_logs.latency_ms`/`tool_rounds`/`tools_called`, porque sem separar "quantas rodadas de tool" de "quantos tokens" não dá para saber se uma resposta lenta foi o modelo ou o número de idas e vindas (é sempre o número de idas e vindas). Leituras (`get_tasks`, `get_flight_info`, `get_itinerary`) ganharam `limit`.

Não há índice GIN de trigrama de propósito: as buscas já são pré-filtradas por `trip_id`, o que reduz o conjunto a algumas centenas de linhas curtas. Um GIN exigiria um wrapper `IMMUTABLE` de `unaccent` e só compensa uma ordem de grandeza acima deste volume.

External setup (manual, not automatable from the repo): Meta app + WhatsApp Business number + permanent token; `supabase secrets set` for `GEMINI_API_KEY`, `META_WA_TOKEN`, `META_WA_VERIFY_TOKEN`, `META_WA_APP_SECRET`, `CRON_SECRET` (all documented in `env.example`); Vault secrets `project_url`/`cron_secret` then re-run the **three** cron migrations (`daily_digest_cron`, `activity_reminders_cron`, `activity_checkins_cron`); webhook URL pointed at `/functions/v1/whatsapp-webhook`; insert a `whatsapp_configs` row per tenant. The daily digest's first outbound message of the day may require an approved **message template** in Meta Business (utility category).

### Excesso de avisos e reconciliação do roteiro com a realidade (2026-09-08)

**Avisos de atividade em excesso.** Um roteiro "touring plan" (item a item, ~15-25min de intervalo) fazia CADA item do dia disparar seu próprio "Daqui a N min!" — dezenas de mensagens/dia por participante, confirmado em produção (`activity_reminders`). `reminderScheduler.ts`/`selectDueReminders` agora dispara só o item mais próximo por execução (evita rajada) e ganhou **cooldown** (`whatsapp_configs.reminder_cooldown_minutes`, default 40min): intervalo mínimo desde o último aviso "normal" da viagem, furado só por override explícito do item ou por a atividade estar a ≤10min do início. `formatActivityReminder` também arredonda a antecedência pra múltiplo de 5 — o valor exato (57, 58...) é sempre um pouco menor que os 60min configurados (o cron só detecta a janela periodicamente) mas lê como "sempre errado" pra família por nunca bater com o número redondo.

**Reconciliação com a realidade.** `supabase/functions/activity-checkins/index.ts` (público, `verify_jwt = false`, gated por `x-cron-secret`, cron `5,20,35,50 * * * *`) detecta itens do roteiro cujo horário (fim, ou início+30min se não houver fim) já passou há mais que `whatsapp_configs.checkin_grace_minutes` (default 20min) sem ninguém marcar como concluído, e manda **uma mensagem em lote** perguntando "isso rolou?" — nunca item a item, mesmo racional dos avisos de horário (ver `_shared/checkinScheduler.ts`/`selectOverdueItemsForCheckin`, teto de 8 itens por mensagem, cooldown próprio via `whatsapp_configs.checkin_cooldown_minutes`, default 90min).

A resposta da família é resolvida pelo chat normal (Gemini function calling), não por esta function — `_shared/tripTools.ts` ganhou:
- `confirm_itinerary_outcome` (title, outcome: done|skipped, note?) — SEM confirmação em duas etapas, ao contrário das outras tools de escrita: a família já está respondendo a uma pergunta direta (do check-in ou espontânea), pedir confirmação de novo seria absurdo. `outcome=done` reusa a lógica de `mark_itinerary_item_done`; `outcome=skipped` faz upsert em `itinerary_item_outcomes` (`status='skipped'`) — **isto é o "banco de atividades não realizadas"**.
- `list_unfulfilled_activities` — lista os itens `status='skipped'`, pra IA sugerir reencaixe.
- `cancel_itinerary_item` — com confirmação em duas etapas (é uma decisão de desistir, diferente de responder uma pergunta): marca `status='cancelled'` (terminal, sai do banco ativo mas fica no histórico; não apaga o item do roteiro).

`reschedule_itinerary_item` e `mark_itinerary_item_done` limpam a linha de `itinerary_item_outcomes` do item ao aplicar (reencaixado ou marcado concluído por fora do check-in = não é mais pendência). Tabela nova `itinerary_item_outcomes` (`pending`/`skipped`/`cancelled`, unique por `itinerary_item_id`) e `whatsapp_messages.kind` ganhou `'checkin'` (mesmo motivo de `digest`/`reminder`: não deve entrar no histórico de chat do Gemini).

**Gap conhecido:** um item cancelado (`status='cancelled'`) continua existindo em `itinerary_items` sem nenhuma marcação visual no app — `ItineraryView`/`DayTimeline` não sabem ler `itinerary_item_outcomes` ainda. Só afeta o bot por enquanto.

## Gotchas

- **`auditEngine.ts` is generic since #31** — every rule reads data (`birth_date`-derived `age`, `height_cm`, flight/accommodation dates, itinerary times), never a name or literal date; each rule is a pure function composed by `runFullTripAudit`, tested in `auditEngine.test.ts` against a *different* family. Eligibility (height/age) lives in `src/services/eligibility.ts`, shared by the audit, `coverageEngine.ts` and `ItineraryView.tsx`. The park catalog (`src/services/roteiro/*`) now carries `minHeightCm` for 56 attractions, so the height gate fires with real data. **`AiCopilotView.tsx` is still the `setTimeout` + keyword chain** — PR #47 (open) replaces it with the `copilot-chat` edge function; don't duplicate that work. `MonthCalendar.tsx` renders one block per month between `start_date` and `end_date` (#33).
- **`DocumentFile` and `LoyaltyAccount` are declared twice** — in `database.types.ts` *and* again in `TripContext.tsx`, which exports its own copies. The context and everything downstream use the `TripContext` versions. Edit both, or consolidate, to avoid drift.
- **`Participant.age` / `is_minor` are derived on read** in `participantMapper.ts` from `birth_date` (the SQL table has no `age` column) and never written. Anything that needs an age must go through the mapper's `deriveAge(birthDate, today)`.
- **tsconfig is strict in ways that break builds late:** `noUnusedLocals` and `noUnusedParameters` turn unused variables into build failures (`npm run dev` won't catch them — only `npm run build`). `verbatimModuleSyntax` requires `import type` for type-only imports. `erasableSyntaxOnly` forbids enums and constructor parameter properties.
- **IDs are `crypto.randomUUID()`** via `newId()` in `src/services/ids.ts`; never reintroduce `` `prefix-${Date.now()}` `` (collides for batch inserts in the same millisecond).
- **`DailyBriefingView` uses the Web Speech API** (`window.speechSynthesis`) directly, guarded by feature detection.
- `README.md` is the untouched Vite starter template and describes nothing about this app.
